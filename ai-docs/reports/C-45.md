# C-45 — Notification permission through the shared PermissionService (D-039 item 3)

Worker A · branch `worker-a` · worktree `../riverpod_core-a`

## What changed
- **One permission flow.** `NotificationPermissionFlow`, `NotificationPermissionBackend`, `PlatformNotificationPermissionBackend` and `notificationRationalePresenterProvider` are deleted. The notification service asks `PermissionService` for `AppPermission.notifications`, and maps the result with `notificationStateOf` (`lib/core/notifications/permission/notification_permission_state.dart`). The mapping keeps the old meaning: limited is granted, restricted is permanently denied, provisional stays provisional.
- **Core permissions** (`lib/core/permissions/`):
  - `AppPermission.notifications` (permission_handler `Permission.notification`).
  - `AppPermissionResult.provisional` (iOS quiet delivery), which is usable.
  - `mapPermissionStatus` and `platformPermissionOf` are top-level and `@visibleForTesting`, so the mapping is tested without the plugin.
  - `PermissionService.openSettings()` is public, so the notification service opens settings through the same service.
- **Rationale copy**: `ds_permissions.notificationsTitle` and `notificationsMessage` in `en.json` and `ar.json`, with a bell icon. The dialog's three switches (icon, title, message) gained the notifications case. The copy is written to read naturally in both languages, and it is LocaleKeys only.
- **Notification providers**: `notificationPermissionState` reads through `permissionServiceProvider`. `notificationServiceProvider` passes `permissionServiceProvider` into `NotificationService`.

## Decisions
- **Presenter wiring stays in the app.** `core/` may not import the design system (ARCHITECTURE, core rules), so the shared dialog reaches the flow only through `permissionRationalePresenterProvider`, which the app overrides with `showPermissionRationale`. The template still defaults it to null, as before, so no rationale is shown until the app wires it. This is the same behaviour as the old notification presenter.
- **The iOS provisional prompt stays on the push backend.** `requestProvisionalPermission` asks Firebase for `provisional: true`. `permission_handler` has no provisional request, so that prompt cannot go through the service. Its result is still mapped by the same notification state mapping.
- **`restricted` no longer opens settings from the notification flow.** The shared service returns restricted as is (its documented rule for every permission), so no rationale or settings prompt is shown for it. The state is still reported as permanently denied, so the notification UI shows the same state. This is a deliberate change to a state the user cannot fix from the prompt.
