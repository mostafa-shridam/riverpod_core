# C-50: rename tool must only rewrite the app's own deep-link scheme

## What
Bug: `rewriteManifestDeepLink` replaced every `android:scheme` except https/http, so the `<queries>` entries `mailto` and `tel` became the app scheme (`my-app`) and mailto:/tel: launching broke in a renamed app.

Fix (`tool/lib/rename_app_logic.dart`):
- `rewriteManifestDeepLink` now touches only `<intent-filter>` blocks that have a VIEW action and the BROWSABLE category. `<queries>` holds `<intent>` elements, so it is never matched. Inside those filters the well-known schemes (http, https, mailto, tel, sms) are kept. `android:host` is rewritten only inside the same filters.
- `validateRename` refuses a package whose scheme is a well-known one (`mailto`, `tel`, `sms`, `http`, `https`).
- Info.plist was already safe: the regex only matches the `CFBundleURLSchemes` entry, `LSApplicationQueriesSchemes` is untouched (now asserted).

## Tests (`test/tool/rename_app_test.dart`)
- Rename on a temp project holding the real manifest and Info.plist of the repo: queries stay `https, http, mailto, tel`, outside queries the schemes are `https, my-app`, plist URL scheme is `my-app`, plist queries unchanged.
- Transform unit test: `<queries>`, `sms`, and a non-VIEW intent-filter are untouched; the transform is idempotent.
- Second rename with other values keeps queries intact; the identical request again is refused.
- Packages `mailto`, `tel`, `sms`, `http`, `https` are refused.

## End to end
Copy of the repo outside the tree, `dart run tool/rename_app.dart --name "My App" --id com.company.myapp`, then `flutter pub get && flutter analyze`: No issues found. Manifest diff against the original is only the label and the app scheme (`riverpod-core` to `my-app`); the `<queries>` section is byte-identical.

## Decisions
None (no new package, no doc change needed: DEEP_LINKS.md already says the scheme lives in the intent-filter).
