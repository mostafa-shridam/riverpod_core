# C-21 — Remote config: force update, maintenance, feature flags (D-040)

Worker A · branch `worker-a` · worktree `../riverpod_core-a`

## What changed
- **Model** (`lib/core/remote_config/remote_config.dart`, freezed): `RemoteConfig` {`minVersion`, `latestVersion`, `storeUrl`, `maintenance`, `flags`} and `RemoteMaintenance` {`enabled`, `message`}. `RemoteConfig.defaults` (`0.0.0`, no maintenance, no flags) is used when nothing is cached and the server is unreachable.
- **Version compare** (`app_version.dart`): `compareVersions` compares `major.minor.patch` by number (`1.10.0 > 1.9.0`); a build number after `+` is ignored; missing parts count as 0; anything else throws `FormatException`.
- **Gate** (`app_gate.dart`): `gateStatusFor` → `AppGateStatus {ok, updateAvailable, updateRequired, maintenance}`. Maintenance wins over updates. An unreadable version never blocks (ok). `softUpdateDue` is true only for an available update the user has not dismissed.
- **Source and repository**: `RemoteConfigSource` with `HttpRemoteConfigSource` (Dio, path from `AppConfig.remoteConfigPath`) and `MockRemoteConfigSource` (`REMOTE_CONFIG_MOCK`). `RemoteConfigRepository.watch()` goes through the existing `CachedRepositoryHelper` (D-038): the cached copy first (stale when older than 1 h), then the server; a failed fetch keeps the cached copy as stale, or errors when nothing is cached.
- **Providers** (`remote_config_provider.dart`, keepAlive): `remoteConfigProvider` (stream), `currentRemoteConfigProvider` (defaults until known), `appGateStatusProvider`, and `flagProvider(name)` (typed `bool`, false by default).
- **Startup** (`startup_controller.dart`): the remote config is an optional step. It waits at most `splashRemoteConfigTimeout` (3 s), logs a warning on failure, and never blocks or fails startup.
- **Router**: `appRedirect` takes `gate`. Maintenance sends every location to the maintenance page; a forced update sends to the force update page, ahead of sign-in and onboarding. Gate pages are left once the gate is ok. The router listens to `appGateStatusProvider`.
- **Pages** (`features/app_gate/presentation/pages/`): `ForceUpdatePage` (`/force-update`) and `MaintenancePage` (`/maintenance`), one per file, `static const routeName`. Store button (via `storeOpenerProvider`, `launchUrl` by default) and a retry button that refetches the config. The maintenance page shows the server's message when it sends one.
- **Soft update**: `DismissedUpdates` (`features/app_gate/providers/app_gate_providers.dart`) keeps the dismissed versions in the prefs string-list slot `app.remoteConfig.dismissedUpdates` (device setting, not per user). `SoftUpdateBanner` (`presentation/widgets/`) shows "later" and "update" actions.
- **Version source** (`remote_config_provider.dart`): `currentAppVersionProvider` is the `APP_VERSION` override when set, else `appInfoProvider` (C-22, `package_info_plus`). The gate compares that version; while it is still loading, or unknown, the gate stays open.
- **Config** (`app_config.dart`, `env/*.env.example`): `APP_VERSION` is optional and blank by default (the installed version is used); when set it must look like `x.y.z`. `REMOTE_CONFIG_PATH` (default `/app/config`, must start with `/`) and `REMOTE_CONFIG_MOCK` (default `false`).
- **Soft update banner mounted** in `lib/core/router/app_shell.dart`: a `Column` with the banner above the tab navigation. It is empty unless an update is due and not dismissed.
- **Translations**: top-level `app_gate` in `en.json` and `ar.json` (`forceUpdate`, `maintenance`, `update`). `lib/generated` regenerated (D-037).

## Decisions
- **Own endpoint, no `firebase_remote_config`** (D-040, already recorded). No new package.
- **The app version comes from C-22 `appInfoProvider`** (`package_info_plus`, D-041). `APP_VERSION` is an optional override for testing the gate. An unknown version never forces an update.
- **Remote config reads do not retry.** Riverpod's default retry re-runs a failed provider for about 30 s and keeps `.future` pending; `remoteConfig` sets `retry` to null, so a failed read ends at once and the app uses the cached copy or the defaults (see Root cause below).
- **Remote config never blocks startup.** The first value waits at most 3 s; a cached copy is used at once when present.
- **Gate precedence**: maintenance, then forced update, then sign-in and onboarding, then the app.
- **No conditional requests yet.** The fetch returns the ETag, but the helper's fetch closure cannot pass the last ETag back, so every revalidation is a full GET. Sending `If-None-Match` needs a helper change (C-44 area).
- **Retention presets**: the `CachePolicy` presets named in D-038 are not in `cache_policy.dart` yet. The 1 h ttl is a constant in the repository only, until C-44 replaces it.

## Root cause of the remote config test timeout (Lead's CHANGES)
- The test "without a config the defaults apply" timed out at 30 s in the Lead's run, then failed with "disposed during loading state".
- Cause: Riverpod 3 retries a provider whose build throws, unless the error is a `ProviderException` or an `Error`. A `NetworkException` was retried 10 times (200 ms doubling, capped at 6.4 s, about 31 s in total), and `remoteConfigProvider.future` stays pending until the retries end. The test passed only after about 39 s.
- Fix: `remoteConfig` has `retry: _noRetry` (returns null), so the first failure is final. The test keeps its assertions and also checks that the source is fetched once. Behaviour change: a failed config read now errors at once; before, it kept retrying in the background for about 30 s. The gate and startup results are unchanged.
- The "without an override" test hung for another reason: it did not call `container.listen` on the stream provider as the other tests do. It now uses the same `_container` helper, which listens.
- The gate suite: 35 remote config tests pass in about 5 s.
