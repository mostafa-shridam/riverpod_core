# HOW TO START A NEW APP FROM THIS TEMPLATE

Status: skeleton. Steps marked (pending C-xx) depend on a task that is not DONE yet; this file is completed by C-29.

1. **Copy the template**: clone/copy the repo, delete `.git`, `git init`, first commit "Initial commit from riverpod_core".
2. **Rename**: from the project root run `dart run tool/rename_app.dart --name "My App" --id com.company.myapp` (add `--package my_app` to override the Dart package name, `--host links.company.com` for the deep-link domain; `--dry-run` only prints the changes). Then run `flutter pub get`.
3. **Environments** (pending C-37, C-08): copy `env/dev.env.example` → `env/dev.env` (same for staging/prod), fill values. Then just `flutter run` (debug = dev, release = prod; staging: `flutter run -t lib/main_staging.dart`). The app refuses to start with a clear error if a required key is missing. Never put real secrets in env files: they are bundled in the app.
4. **Firebase** (only if you use notifications/crash): add your own `google-services.json` and `GoogleService-Info.plist` locally. They are git-ignored; never commit them.
5. **Branding**: edit ONLY `lib/core/design_system/tokens/brand_config.dart` (seed color, font) (pending C-05).
   - **Icon**: replace `assets/images/app_icon.png` (1024 px, full icon) and `assets/images/app_icon_foreground.png` (1024 px, transparent, artwork inside the central 66%) with your own art (the placeholders come from `dart run tool/generate_placeholder_icon.dart`, which uses the seed color). Set `adaptive_icon_background` in the `flutter_launcher_icons` block of `pubspec.yaml`, then run `dart run flutter_launcher_icons` and commit the generated Android and iOS files. If it rewrites `ASSETCATALOG_COMPILER_GENERATE_SWIFT_ASSET_SYMBOL_EXTENSIONS` in `ios/Runner.xcodeproj/project.pbxproj` to `AppIcon`, revert that line to `YES`.
   - **Native splash**: set the colors and image in the `flutter_native_splash` block of `pubspec.yaml` (same color as the seed), then run `dart run flutter_native_splash:create` and commit. If it re-indents `ios/Runner/Info.plist`, keep only the real changes.
   - **Deep links**: see `ai-docs/DEEP_LINKS.md`. Pass your domain to the rename tool (`--host links.company.com`) or edit the four places listed there, then publish `assetlinks.json` and `apple-app-site-association`.
6. **Translations**: edit `assets/translations/{ar,en}.json`, run the generation commands in `build.sh`; the parity test must stay green.
7. **First feature**: run `dart run tool/new_feature.dart --name product_orders` (`--dry-run` only prints the plan). It scaffolds the feature and its tests from `.fttemplates/feature`, adds its translation keys to both files and prints the typed route to paste into `lib/core/router/routes.dart`; then follow `.claude/skills/new-feature/SKILL.md` (generation commands, tests).
8. **Gate before every commit**: the Definition of Done commands in `CLAUDE.md`.
9. **Release** (pending C-28): `.claude/skills/release-check/SKILL.md`, signing files stay untracked.

## Toolchain requirements (C-43)
Verified versions: Flutter 3.47 (Dart per `pubspec.yaml`), JDK 17+ (21 works), Gradle wrapper 8.14.3, Android Gradle Plugin 8.11.1, Kotlin Gradle plugin 2.4.0 (plugins ship Kotlin 2.4 metadata, so the project plugin must be >= 2.4), `compileSdk` 37 (required by `permission_handler_android`), `minSdk` 24, Java/Kotlin target 17, NDK from Flutter (28.2), iOS deployment target 15.0 with CocoaPods (`pod install` runs on the first iOS build). Create `env/{dev,staging,prod}.env` from the examples before the first build. Release builds need `android/key.properties` (see `tool/release/README.md`). Flutter warns that Gradle < 9.1 and AGP < 9.0.1 will be dropped soon; plan that upgrade as its own task once the Firebase and other plugins support AGP 9.

## Native flavors (D-043)
The template has no Android `productFlavors` and no iOS schemes, so plain `flutter run` works. Environments are `Flavor.current` (debug = dev, release = prod) and `lib/main_staging.dart` (D-024). Add native flavors only when one device must hold several environments (different application id, name or icon per environment):
1. Android, `android/app/build.gradle.kts`: add `flavorDimensions += "env"` and `productFlavors { create("dev") { dimension = "env"; applicationIdSuffix = ".dev"; resValue("string", "app_name", "MyApp Dev") } ... }` (also `staging`, `prod`); point `android:label` at `@string/app_name`. Per-flavor google-services.json goes in `android/app/src/<flavor>/`.
2. iOS: duplicate the Runner scheme per environment, add Debug/Release/Profile configurations suffixed `-dev` etc., set `PRODUCT_BUNDLE_IDENTIFIER` and display name per configuration, and per-flavor `GoogleService-Info.plist` through a build phase.
3. Run with `flutter run --flavor dev -t lib/main.dart` (staging: `--flavor staging -t lib/main_staging.dart`). From then on every run and build needs `--flavor`: update `tool/release/README.md`, CI and the docs of the app.
4. Deep links: give each flavor its own scheme (manifest placeholders on Android, per-configuration `CFBundleURLSchemes` on iOS) and keep `deepLinkScheme` in step. Record the change as a DECISION in the app repo.
